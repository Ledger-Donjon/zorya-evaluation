# P-224 Elliptic Curve Carry Bug (CVE-2021-3114)

**Bug class**: Silent arithmetic error (wrong field element — no panic, no crash)  
**Project**: [golang/go](https://github.com/golang/go) — Go standard library `crypto/elliptic`  
**Vulnerable versions**: Go 1.0 – 1.15.8 / 1.16.0  
**Fix commit**: [`d95ca91`](https://github.com/golang/go/commit/d95ca911af89a0a3e571ced0c0a5be8a43b41571) (Go 1.15.9 / 1.16.1)  
**CVE**: [CVE-2021-3114](https://nvd.nist.gov/vuln/detail/CVE-2021-3114)  
**Go issue**: https://github.com/golang/go/issues/43786

---

## Vulnerability

`crypto/elliptic/p224.go` implements the P-224 finite field via a radix-2²⁸
limb representation. The function `p224Contract` performs the final complete
reduction modulo P-224 = 2²²⁴ − 2⁹⁶ + 1. It contains **two bugs** that produce
silently wrong field elements without any panic or runtime error.

### Bug 1 — Inverted `out3GT` mask (sign error)

```go
// VULNERABLE (go1.14.13, p224.go)
n := out[3] - 0xffff000    // BUG1a: subtraction is backwards
out3GT := ^uint32(int32(n) >> 31)  // BUG1b: should be uint32(...), not ^uint32(...)

// FIXED (commit d95ca91)
n := 0xffff000 - out[3]
out3GT := uint32(int32(n) >> 31)
```

The condition "is `out[3]` greater than `0xffff000`?" uses the wrong operand
order and then negates the result. The subtraction sign is flipped **and** the
bit-mask is complement-negated, meaning `out3GT` is `1` when it should be `0`
and vice versa.

### Bug 2 — Missing carry-down after conditional P-subtraction

When the conditional subtraction `out[0] -= 1 & mask` fires with `out[0] == 0`,
the result wraps to `0xFFFFFFFF` — a silent `uint32` underflow. The fixed code
adds a carry-down loop after the subtraction:

```go
// FIXED: carry-down loop that was missing in the vulnerable version
for i := 0; i < 3; i++ {
    mask := uint32(int32(out[i]) >> 31)
    out[i] += (1 << 28) & mask
    out[i+1] -= 1 & mask
}
```

### Security impact

`p224Contract` is called by every P-224 point arithmetic operation
(`p224Add`, `p224Mul`, `p224Square`). Wrong field elements propagate silently
into ECDH shared secrets and ECDSA signatures. An attacker can recover private
keys or forge signatures for any P-224 key pair generated by the vulnerable Go
standard library. The Go Security team rated this as **high severity**.

### Triggering input

The limb vector below directly exercises Bug 2 (used as seed corpus in
`fuzz/fuzz_no_oracle_test.go`):

```
in = [0, 1, 0, 0x0ffff000, 0xfffffff, 0xfffffff, 0xfffffff, 0xfffffff]
```

Expected output (correct reduction): `26959944256743573406181601774076492161814012476721817469321081782272`  
Buggy output: `26959942750239151301211910195871123182912241769479406753892278468607`

## Why neither Zorya nor `go test -fuzz` finds this bug

### Zorya — blocked by `runtime.memmove`

Running Zorya on the compiled `p224Contract` function (`--mode function 0x4d7840`)
produces the following trace before the engine halts:

```
Address: 4d7840, Symbol: crypto/elliptic.p224Contract
Address: 4659e0, Symbol: runtime.memmove
```

The very first statement of `p224Contract` is:

```go
copy(out[:], in[:])
```

The Go compiler lowers this `copy` call to `runtime.memmove`. Zorya's concolic
engine does not model `memmove` semantically; when execution reaches that call
the engine cannot propagate symbolic taint through the raw memory-copy loop and
halts. Because the taint never reaches the buggy carry arithmetic further in the
function, Zorya produces no findings.

This is a **tool limitation**, not a property of the bug itself: if the `copy`
were replaced by an explicit loop (`for i := range in { out[i] = in[i] }`) Zorya
would be able to continue and could in principle reach the vulnerable arithmetic.

### `go test -fuzz` — blind without a differential oracle

Coverage-guided fuzzing stops only when it observes a **crash** (panic,
`runtime.throw`, signal, non-zero exit). `p224Contract` — and every function
built on top of it — never panics; it merely returns a mathematically wrong
`[8]uint32`. The fuzzer has no way to know the output is wrong.

Empirical confirmation (from running both fuzz targets in `fuzz/`):

| Target | Mode | Duration | Result |
|---|---|---|---|
| `FuzzP224_NoOracle` | coverage-only (no correctness check) | 2 min / ~89 M execs | **PASS** — 0 findings |
| `FuzzP224_WithOracle` | differential oracle vs. `math/big` | 0.03 s / 3 execs | **FAIL** — bug found |

The no-oracle run executed more than **89 million** inputs including the exact
bug-triggering seed, yet reported no failure:

```
fuzz: elapsed: 2m0s, execs: 89111775 (739745/sec), new interesting: 0 (total: 3)
--- PASS: FuzzP224_NoOracle (120.10s)
```

With a differential oracle (`FuzzP224_WithOracle`) that compares the buggy
function against a `math/big`-based reference, the bug is found on the **third
execution** in under one second:

```
--- FAIL: FuzzP224_WithOracle (0.03s)
    fuzz_oracle_test.go:46: p224Contract wrong!
          in  = [0 1 0 268431360 268435455 268435455 268435455 268435431]
          expected = 26959944256743573406181601774076492161814012476721817469321081782272
          got      = 26959942750239151301211910195871123182912241769479406753892278468607
```

The oracle seeds are the same limb values already present in the no-oracle
corpus — the fuzzer had them all along; it just had no signal to act on them.

## Comparison with Other Analysis Tools

All tools below were run against the same vulnerable code. **None of them detect
the carry bug** — for the same structural reason: `p224Contract` returns a wrong
value silently, with no panic, no signal, and no crash.

### BINSEC (binary-level static symbolic execution)

BINSEC uses a core snapshot taken at the function entry, then symbolizes the
input arguments and explores all reachable paths, asserting at known panic
sites.

#### 1. Create a GDB core snapshot at the function entry

```bash
gdb --args /tmp/p224-driver 0000000000000000000000000001
(gdb) break *0x4d7840
(gdb) run
# GDB stops at p224Contract entry
(gdb) delete breakpoints    # avoids INT3 byte in the snapshot
(gdb) generate-core-file /tmp/p224-core.snapshot
(gdb) quit
```

> Replace `0x4d7840` with the address from:
> `go tool nm /tmp/p224-driver | grep p224Contract`

#### 2. Write the BINSEC configuration script

Save as `binsec-findings/binsec_p224.ini`:

```ini
# Binsec SSE configuration for p224-elliptic-2021
# Target: crypto/elliptic.p224Contract
# Binary: /tmp/p224-driver
# Function entry: 0x4d7840
#
# Go 1.17+ register ABI:
#   RAX = out *P224FieldElement   (pointer to output [8]uint32)
#   RBX = in  *P224FieldElement   (pointer to input  [8]uint32)
#
# Symbolize the 8 uint32 limbs of the input array (pointed to by RBX).
# Each limb is 4 bytes; the full array is 32 bytes.

starting from core

# ── Symbolize in[0..7] (the 8 limbs at *rbx) ──────────────────────────────
@[rbx+0,  4] := nondet as limb0
@[rbx+4,  4] := nondet as limb1
@[rbx+8,  4] := nondet as limb2
@[rbx+12, 4] := nondet as limb3
@[rbx+16, 4] := nondet as limb4
@[rbx+20, 4] := nondet as limb5
@[rbx+24, 4] := nondet as limb6
@[rbx+28, 4] := nondet as limb7

# Restrict to valid 28-bit limbs (radix-2^28 representation)
assume limb0 <= 0x1fffffff
assume limb1 <= 0x1fffffff
assume limb2 <= 0x1fffffff
assume limb3 <= 0x1fffffff
assume limb4 <= 0x1fffffff
assume limb5 <= 0x1fffffff
assume limb6 <= 0x1fffffff
assume limb7 <= 0x1fffffff

explore all

# ── Stub runtime.morestack (prevents early syscall path cut) ───────────────
replace <runtime.morestack> by
  return
end
replace <runtime.morestack_noexit> by
  return
end

# ── Stub runtime.memmove (copy at top of p224Contract) ────────────────────
# The function begins with copy(out[:], in[:]) → runtime.memmove.
# Binsec cannot interpret the raw memory-copy loop; stub it so the
# symbolized limbs remain in rbx memory and exploration continues.
replace <runtime.memmove> by
  return
end

# ── Abort at Go runtime panic entry points ─────────────────────────────────
# The carry bug does NOT trigger any of these — it is a silent wrong result.
abort at <runtime.panicmem>
abort at <runtime.gopanic>
abort at <runtime.panicdivide>
abort at <runtime.panicIndex>
abort at <runtime.panicSliceB>
abort at <runtime.panicnildereference>

# ── No overflow / arithmetic-correctness oracle ────────────────────────────
# The inverted mask (BUG1) and the missing carry-down (BUG2) both produce
# wrong uint32 values without any branch change or panic.
# Binsec has no built-in mechanism to assert that the output limbs represent
# a fully-reduced field element — detecting this would require an explicit
# postcondition such as:
#   assert out[0] < 2^28 && out[3] <= 0xffff000 && ...
# which is not added here (faithfully reproducing the no-oracle scenario).
```

#### 3. Run BINSEC

```bash
binsec -sse \
       -sse-script binsec-findings/binsec_p224.ini \
       -sse-depth 10000 \
       /tmp/p224-core.snapshot
```

**Expected result**: `failed assertions: 0` — no findings. The `runtime.memmove`
stub allows exploration to continue past the `copy`, but the buggy carry
arithmetic produces no assertion failure. Both bugs are invisible to
crash-based analysis.

### SymQEMU (input-driven binary-level concolic execution)

SymQEMU tracks bytes from `argv`, `stdin`, and file reads symbolically and
generates new test cases whenever a symbolic branch diverges.

#### 1. Setup

```bash
export SYMQEMU_BIN=/home/kgorna/symqemu/build/qemu-x86_64
export SYMCC_OUTPUT_DIR=/tmp/symqemu-p224-output
export SYMCC_ENABLE_LINEARIZATION=1
mkdir -p /tmp/symqemu-p224-output
```

#### 2. Run SymQEMU

The driver binary reads the P-224 limb input from `argv[1]` as a hex string.
All bytes of `argv[1]` are automatically tracked symbolically by SymQEMU.

```bash
echo "" | $SYMQEMU_BIN /tmp/p224-driver \
    0000000000000000000000000001 \
    2>&1 | tee symqemu-findings/symqemu-symbolic.log

# Check whether any new test cases were generated
ls -la /tmp/symqemu-p224-output/
```

#### 3. Check results

```bash
ls -la /tmp/symqemu-p224-output/
```

**Expected result**: empty output directory — zero test cases generated.

**Why SymQEMU fails**:

1. **No crash to observe**: even when symbolic limb bytes reach the carry
   arithmetic, the wrong `uint32` result causes no branch divergence, no
   signal, and no non-zero exit. SymQEMU generates new inputs only when a
   concrete path branches differently from the symbolic path, or when a crash
   occurs. Neither happens here.

2. **Hex-parsing decouples argv bytes from limb values**: the driver converts
   the hex string to `uint32` limbs through a parsing loop. SymQEMU may lose
   symbolic tracking across the multi-step decode (hex nibble → byte → uint32
   little-endian assembly), especially across Go slice indexing with symbolic
   indices.

### Nilaway (nil-flow static analysis)

[Nilaway](https://github.com/uber-go/nilaway) is Uber's inter-procedural nil
safety analyser for Go. It performs whole-program inference to determine which
values can be nil at a dereference site, going substantially beyond what
`go vet` or `staticcheck` can track.

```bash
# Install
go install go.uber.org/nilaway/cmd/nilaway@latest

cd ~/Documents/evaluation/go-compiler/p224-elliptic-2021/fuzz
nilaway ./...
```

**Expected output**: *(no output — clean exit)*

**Why it misses the bug**: Nilaway's analysis is scoped to **nil pointer
safety** — it tracks whether a pointer-typed value can be nil at the point
where it is dereferenced. The p224-elliptic-2021 bug is categorically
different:

- `out` and `in` are non-nil stack-allocated arrays passed by pointer; no nil
  dereference is possible.
- BUG1 (inverted `out3GT` mask) and BUG2 (missing carry-down loop) are errors
  in **integer arithmetic**, not in pointer management.

Nilaway has no model of field-element reduction correctness, bitwise mask
semantics, or carry-chain invariants. From its perspective, the function is
entirely nil-safe.

## GoLibAFL Fuzzing

`p224Contract` produces a **silently wrong field element** — no panic, no crash. Without a differential oracle, GoLibAFL (like all crash-based fuzzers) runs indefinitely with zero findings. With an oracle that compares against `math/big`, the `panic()` call is caught as a SIGSEGV crash.

### Harness (no oracle — does NOT detect the bug)

> **Note**: `p224Contract` is provided by `vuln_p224.go` (vendored in the same
> `package main` — see Step 2 of the build instructions below). No `//go:linkname`
> is needed; calling the stdlib symbol directly would cause a linker error because
> the vulnerable function is not exported from the standard library binary.

```go
package main

// #include <stdint.h>
// #include <stddef.h>
import "C"

// P224FieldElement and P224Contract_Buggy are defined in vuln_p224.go (same package).

func harness(data []byte) {
    if len(data) < 32 {
        return
    }
    var in P224FieldElement
    for i := 0; i < 8; i++ {
        in[i] = uint32(data[i*4]) | uint32(data[i*4+1])<<8 |
            uint32(data[i*4+2])<<16 | uint32(data[i*4+3])<<24
    }
    var out P224FieldElement
    P224Contract_Buggy(&out, &in)
    // Wrong result — no signal. Fuzzer never finds the bug.
}

// Do NOT declare func main() — GoLibAFL provides it in harness_fuzz.go.
```

**Result**: Runs indefinitely — no crash, no detection.

### Harness (with differential oracle — detects the bug)

```go
package main

// #include <stdint.h>
// #include <stddef.h>
import "C"
import (
    "math/big"
)

// P224FieldElement and P224Contract_Buggy are defined in vuln_p224.go (same package).

// p224P is the P-224 prime: 2^224 - 2^96 + 1
var p224P, _ = new(big.Int).SetString(
    "26959946667150639794667015087019630673637144422540572481103610249215", 10)

func limbsToBig(limbs P224FieldElement) *big.Int {
    result := new(big.Int)
    for i := 7; i >= 0; i-- {
        result.Lsh(result, 28)
        result.Or(result, new(big.Int).SetUint64(uint64(limbs[i]&0xfffffff)))
    }
    return result
}

func harness(data []byte) {
    if len(data) < 32 {
        return
    }
    var in P224FieldElement
    for i := 0; i < 8; i++ {
        in[i] = uint32(data[i*4]) | uint32(data[i*4+1])<<8 |
            uint32(data[i*4+2])<<16 | uint32(data[i*4+3])<<24
    }

    // Oracle: compute expected result (correct modular reduction)
    input := limbsToBig(in)
    expected := new(big.Int).Mod(input, p224P)

    // Run vulnerable function (defined in vuln_p224.go, same package)
    var out P224FieldElement
    P224Contract_Buggy(&out, &in)
    got := limbsToBig(out)

    if expected.Cmp(got) != 0 {
        panic("p224Contract wrong: input=" + input.String() +
            " expected=" + expected.String() +
            " got=" + got.String())
    }
}

// Do NOT declare func main() — GoLibAFL provides it in harness_fuzz.go.
```

The wrong field element is returned silently with no crash signal.

#### Step 6 — Fuzz with oracle and bug-triggering seed

The seed encodes the 8-limb vector `[0, 1, 0, 0x0ffff000, 0xfffffff, 0xfffffff, 0xfffffff, 0xfffffff]`
as 32 little-endian bytes — the same input that causes the inverted `out3GT` mask to fire:

```bash
mkdir -p harnesses/p224-oracle/seeds
python3 -c "
import struct, sys
limbs = [0, 1, 0, 0x0ffff000, 0xfffffff, 0xfffffff, 0xfffffff, 0xfffffff]
sys.stdout.buffer.write(struct.pack('<8I', *limbs))
" > harnesses/p224-oracle/seeds/bug_trigger
rm -rf output
cargo run --release -- fuzz --input harnesses/p224-oracle/seeds/
```

**Expected result**: All 24 clients hit an objective on execution 1, run time 0s —
the oracle detects the mismatch immediately from the seed before any mutation.

**Why no seed was needed here** (unlike `evm-gascost-2017` and `tendermint-voting-2018`):

| Bug | Oracle fires when… | Fraction of input space |
|-----|-------------------|------------------------|
| EVM gas overflow | `newMemSize ≥ 0xffffffffe1` | ~1 in 2³² of 64-bit space |
| Tendermint IMUL | `totalVotingPower ≥ MaxInt64/2+1` | ~1 in 4 of int64 space (but positive half only: ~1 in 2) |
| **p224 BUG1** | `out[3] > 0x0ffff000` after contraction | wide region — random 32-bit mutation hits this quickly |

For p224, BUG1 (the inverted `out3GT` mask) fires for any input where limb 3 is large
enough that the wrong branch is taken in the final reduction — a much broader target than a
single 64-bit boundary. Random mutation reaches a triggering input within ~8M executions;
for the EVM overflow, the equivalent region is so narrow that uniform 64-bit mutation
essentially never finds it.

**Key contrast**: `go test -fuzz` with the same oracle also finds it immediately
(3 executions from seed corpus). But `go test -fuzz` *without* oracle runs 89M
executions with 0 findings — the wrong field element is silent. GoLibAFL without
oracle would also run forever. **The oracle is the critical ingredient; the seed
is optional for this bug but mandatory for the overflow cases.**

### Comparison with `go test -fuzz`

| Aspect | `go test -fuzz` (oracle) | GoLibAFL (oracle) |
|--------|--------------------------|-------------------|
| Instrumentation | Go native sancov | Go native sancov (same) |
| Signal | `t.Errorf` → test failure | `panic()` → SIGSEGV → crash file |
| Detection speed | Seed corpus (< 0.1 s) | ~1m 30s / ~8M execs (no seed needed) |
| Throughput | ~740k exec/s | ~83–93k exec/s (24 clients) |
| No-oracle result | PASS — 89M execs, 0 findings (silent) | Runs forever — no crash signal |
| With-oracle result | **Detected on seed corpus (3 execs)** | **Detected in 1m 30s without a seed** |
| Seed required? | No — seed already in corpus | No — oracle fires for wide input range |
| Setup complexity | Trivial | Requires Rust + Cargo; vendor `vuln_p224.go` into harness |

**Conclusion**: The differential oracle is the critical ingredient for both tools — without it, neither detects this silent arithmetic error. Unlike the `evm-gascost-2017` and `tendermint-voting-2018` overflows (where the oracle fires only in a tiny slice of the input space requiring a hand-crafted seed), p224's BUG1 fires for any input where `out[3] > 0x0ffff000` — a broad enough region that GoLibAFL's random mutation reaches it in ~1.5 minutes without any seed. `go test -fuzz` with oracle is faster because it has the bug-triggering seed in the corpus from the start; GoLibAFL finds it independently through mutation alone.
